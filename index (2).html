1. ¿Por qué los DROP TABLE al inicio NO usan CASCADE?

El script borra las tablas en orden inverso (de las más dependientes como verificacion_documento hasta las catálogos base como rol) sin usar DROP TABLE ... CASCADE. ¿Por qué? Porque CASCADE destruiría silenciosamente llaves foráneas en otras tablas si el orden estuviera mal, ocultando errores de dependencia y rompiendo la integridad referencial del modelo.

2. Trigger trg_usuario_normalizar_correo → fn_normalizar_correo_usuario()

Se dispara BEFORE INSERT OR UPDATE OF correo ON usuario:

  • Convierte automáticamente el correo a minúsculas y quita espacios externos (lower(btrim(NEW.correo))) antes de que el CHECK lo evalúe.
  • Si es un UPDATE y el correo cambió (NEW.correo IS DISTINCT FROM OLD.correo), reinicia correo_verificado := FALSE para obligar a validar el nuevo correo.

3. Trigger trg_verificacion_activar_comerciante → fn_activar_comerciante()

Se dispara AFTER INSERT ON verificacion_documento y resuelve una regla multi-tabla que un CHECK no puede hacer:

  • Bloqueo de concurrencia (FOR UPDATE): Bloquea la fila del comercio en estado PENDIENTE_VERIFICACION para evitar que dos aprobaciones simultáneas se pisen.
  • Lista dinámica de documentos (TEXT[] + unnest): Exige los 4 documentos base de persona (CEDULA_FRENTE, CEDULA_REVERSO, SELFIE_CEDULA, CUENTA_COBRO) y suma requisitos según el perfil: EVIDENCIA_ACTIVIDAD si es emprendedor, FACHADA si tiene local físico, RUT si es formal, y CAMARA_COMERCIO + CEDULA_REP_LEGAL si es persona jurídica.
  • Activación en cadena: Si v_faltan = 0 y el comercio tiene al menos una categoría activa en categoria_comercio, actualiza comercio.estado = 'ACTIVO' y también activa el rol comerciante en usuario_rol.
