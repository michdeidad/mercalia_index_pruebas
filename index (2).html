#01

rol

Tabla Principal
Módulo: Usuarios y Seguridad
¿Por qué existe esta entidad? (Propósito de Negocio)

Catálogo maestro de perfiles del sistema (CLIENTE, COMERCIANTE, ADMINISTRADOR). Separa la identidad de la persona de los permisos o capacidades que puede ejercer dentro de Mercalia.

Llaves y Unicidad (PK / FK / UQ)
  • •PK: rol_id (INT GENERATED ALWAYS AS IDENTITY)
  • •UNIQUE: uq_rol_nombre (nombre)
Anatomía de Constraints (CHECK & Reglas)
  • ▪ck_rol_nombre: Restringe los valores estrictamente a CLIENTE, COMERCIANTE o ADMINISTRADOR (validado tanto con IN como con expresión regular ~).
  • ▪NOT NULL en nombre (VARCHAR(15)).
Preguntas Tipo Jurado (Toca para ver la respuesta modelo)
Sustentación: Porque en Mercalia un mismo usuario puede ser CLIENTE (comprar) y al mismo tiempo COMERCIANTE (vender) o ADMINISTRADOR. Normalizar los roles en una tabla maestra permite asignarlos dinámicamente mediante la tabla puente usuario_rol sin duplicar cuentas ni correos.
Sustentación: Es el estándar SQL moderno (desde PostgreSQL 10). Impide que alguien inserte manualmente un ID saltándose la secuencia (a menos que use OVERRIDING SYSTEM VALUE), evitando colisiones de llave primaria.

usuario

Tabla Principal
Módulo: Usuarios y Seguridad
¿Por qué existe esta entidad? (Propósito de Negocio)

Entidad central de identidad, autenticación, cumplimiento legal (Habeas Data / Ley 1581) y reputación global de cualquier persona registrada en Mercalia.

Llaves y Unicidad (PK / FK / UQ)
  • •PK: usuario_id (INT GENERATED ALWAYS AS IDENTITY)
  • •UNIQUE: uq_usuario_correo (correo)
Anatomía de Constraints (CHECK & Reglas)
  • ▪chk_telefono: Expresión regular ^3[0-9]{9}$ que garantiza celulares colombianos válidos de 10 dígitos iniciando en 3.
  • ▪ck_usuario_correo: Obliga a que correo = lower(correo) y cumpla formato válido de email.
  • ▪ck_usuario_puntuacion: Evita incoherencias matemáticas: si total_calificaciones = 0, puntuacion_promedio debe ser 0, y siempre entre 0 y 5.
  • ▪ck_usuario_totp: Si totp_activo es TRUE (2FA), obliga a que totp_secreto NO sea NULL.
  • ▪Campos legales NOT NULL: acepto_terminos_en, version_terminos, autorizo_datos_en e ip_aceptacion (tipo INET).
Preguntas Tipo Jurado (Toca para ver la respuesta modelo)
Sustentación: Por cumplimiento legal (Habeas Data / Ley 1581 de 2012 en Colombia). Garantiza trazabilidad probatoria de cuándo, desde qué IP y bajo qué versión contractual el usuario autorizó el tratamiento de sus datos personales.
Sustentación: Permite invalidar sesiones JWT o tokens activos de forma inmediata. Si un usuario cambia su contraseña o es suspendido, el backend incrementa version_sesion y cualquier token viejo con una versión menor queda rechazado.
#03

usuario_rol

Tabla Asociativa / PK Compuesta
Módulo: Usuarios y Seguridad
¿Por qué existe esta entidad? (Propósito de Negocio)

Resuelve la relación muchos-a-muchos (N:M) entre usuario y rol, controlando el ciclo de vida de cada rol por separado (por ejemplo, un usuario puede estar ACTIVO como cliente pero PENDIENTE o EN_REVISION como comerciante).

Llaves y Unicidad (PK / FK / UQ)
  • •PK Compuesta: pk_usuario_rol (usuario_id, rol_id)
  • •FK: fk_usuario_rol_usuario -> usuario(usuario_id)
  • •FK: fk_usuario_rol_rol -> rol(rol_id) ON UPDATE CASCADE ON DELETE RESTRICT
Anatomía de Constraints (CHECK & Reglas)
  • ▪ck_usuario_rol_estado: Estados válidos PENDIENTE, EN_REVISION, ACTIVO, RECHAZADO, SUSPENDIDO.
  • ▪ON DELETE RESTRICT en rol: Impide borrar un rol del catálogo si existen usuarios asociados a él.
Preguntas Tipo Jurado (Toca para ver la respuesta modelo)
Sustentación: Porque la regla de negocio establece que un usuario no puede tener el mismo rol asignado dos veces. Usar (usuario_id, rol_id) como PK garantiza unicidad natural y además permite que otras tablas (como comercio o bitacora_auditoria) hagan llaves foráneas compuestas hacia esta pareja exacta.
Sustentación: Se inserta una nueva fila en usuario_rol con rol_id de COMERCIANTE en estado PENDIENTE. Su rol de CLIENTE sigue ACTIVO sin interrupciones hasta que el trigger fn_activar_comerciante apruebe su documentación.

categoria_producto

Tabla Principal
Módulo: Comercios y Catálogo

Árbol jerárquico (autorreferenciado) de categorías y subcategorías para clasificar productos (ej. Bebidas -> Bebidas Frías -> Jugos Naturales).

Llaves y Unicidad (PK / FK / UQ)
  • •PK: categoria_producto_id (INT GENERATED ALWAYS AS IDENTITY)
  • •FK Autorreferenciada: fk_categoria_producto_padre -> categoria_producto(categoria_producto_id)
  • •UNIQUE: uq_categoria_producto_nombre UNIQUE NULLS NOT DISTINCT (categoria_padre_id, nombre)
Anatomía de Constraints (CHECK & Reglas)
  • ▪ck_categoria_producto_padre: Evita ciclos directos impidiendo que una categoría sea padre de sí misma (categoria_padre_id <> categoria_producto_id).

Preguntas Tipo Jurado (Toca para ver la respuesta modelo)
Sustentación: En SQL estándar, dos valores NULL se consideran distintos, por lo que un UNIQUE normal permitiría crear dos categorías raíz llamadas "Comida" con categoria_padre_id = NULL. comercio

Tabla Principal
Módulo: Comercios y Catálogo
¿Por qué existe esta entidad? (Propósito de Negocio)

Núcleo de las tiendas, emprendimientos y locales registrados en Mercalia. Contiene su perfil público, modalidad operativa, datos legales/tributarios, métodos de pago y reputación.

Llaves y Unicidad (PK / FK / UQ)
  • •PK: comercio_id (INT GENERATED ALWAYS AS IDENTITY)
  • •UNIQUE: uq_comercio_slug (slug)
  • •FK Compuesta: fk_comercio_usuario_rol (usuario_id, rol_id) -> usuario_rol(usuario_id, rol_id)
  • •FK: fk_comercio_direccion -> direccion(direccion_id)
Anatomía de Constraints (CHECK & Reglas)
  • ▪ck_comercio_local: Bicondicional (modalidad = 'LOCAL_FISICO') = (direccion_id IS NOT NULL). Si es local físico DEBE tener dirección; si es emprendedor virtual NO tiene dirección física asociada.
  • ▪ck_comercio_juridica: Si tipo_persona = 'JURIDICA', exige obligatoriamente que es_formal = TRUE y razon_social IS NOT NULL.
  • ▪ck_comercio_formal: Si es_formal = TRUE, exige NIT obligatorio.
  • ▪ck_comercio_radio: Solo permite radio_entrega_km > 0 si ofrece_domicilio = TRUE.
  • ▪ck_comercio_pagos: Exige que acepte al menos transferencia o efectivo (acepta_transferencia OR acepta_efectivo).

Preguntas Tipo Jurado (Toca para ver la respuesta modelo)
Sustentación: Para garantizar integridad referencial de rol: asegura a nivel de base de datos que el usuario dueño del comercio realmente tiene asignado el rol COMERCIANTE en usuario_rol, y permite al trigger activar exactamente ese par (usuario_id, rol_id).
Sustentación: Usa una equivalencia booleana: (modalidad = 'LOCAL_FISICO') = (direccion_id IS NOT NULL). Ambas expresiones deben ser TRUE o ambas FALSE; es decir, prohíbe un local físico sin dirección y prohíbe un emprendedor sin local con dirección física asignada.

Trigger #1 · BEFORE INSERT OR UPDATE

Normalización Automática y Seguridad de Correo (fn_normalizar_correo_usuario)

Se ejecuta antes de insertar o actualizar la columna "correo" en la tabla usuario.

  • ✓Limpia espacios laterales con btrim() y convierte a minúsculas con lower() antes de que se evalúe el constraint ck_usuario_correo, evitando rechazos innecesarios si el usuario digitó mayúsculas o espacios.
  • ✓Seguridad de cuenta: Si es un UPDATE y el correo cambió (NEW.correo IS DISTINCT FROM OLD.correo), automáticamente reinicia NEW.correo_verificado := FALSE para obligar al usuario a validar su nuevo correo.
CREATE OR REPLACE FUNCTION fn_normalizar_correo_usuario()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    NEW.correo := lower(btrim(NEW.correo));
    IF TG_OP = 'UPDATE' AND NEW.correo IS DISTINCT FROM OLD.correo THEN
        NEW.correo_verificado := FALSE;
    END IF;
    RETURN NEW;
END;
$$;
